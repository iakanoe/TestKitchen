# CONF: Configuration and conventions

The project's `kitchen.yml`, the path globs and file classification built on it, and the fixed conventions every Test Kitchen script reads the same way: ticket and requirement ID formats, test tags, the no-trace marker, test-command placeholders, how git is called, and the shared library's own command line.

- CONF-R01: (observed in code) The configuration is read from `kitchen.yml` at the repository root; a missing file is an error that says it was not found and to run init.py, a file that is not valid YAML is an "invalid YAML" error, a file whose content is not a mapping is an error saying it must be a mapping, and an empty file is read as a mapping with no keys.
- CONF-R02: (observed in code) `tests` and `code` are required, each a non-empty list of non-blank glob strings; a missing key gives an error with an example value, and any other shape gives an error showing the value received.
- CONF-R03: (observed in code) `test_command` is required and must be a non-empty string; which placeholders it contains is not checked when the configuration is loaded.
- CONF-R04: (observed in code) A key outside the known set (`tests`, `code`, `test_command`, `check_command`, `verify`, `host`, `autonomy`, `split_threshold`, `self_contained_tickets`, `releases`, `ignore`) is an error that names it and lists the known keys.
- CONF-R05: (observed in code) Loading reports every configuration problem at once, one line per problem, each prefixed `kitchen.yml:`, and returns no configuration while any problem remains.
- CONF-R06: (observed in code) Optional keys default to: no `check_command`, no `verify`, `autonomy: merge`, `split_threshold: 6`, `self_contained_tickets: false`, release slices off, and an empty `ignore` list; surrounding whitespace is trimmed from glob strings and from `test_command`, `check_command`, and `verify`.
- CONF-R07: (observed in code) Optional values are validated: `check_command` and `verify` are non-empty strings when set (a key left without a value counts as absent; a blank string is an error); `autonomy` is one of `merge`, `pr`, `supervised`; `split_threshold` is a positive whole number (true/false and decimals are refused); `self_contained_tickets` is true or false; `ignore` is a list of non-blank glob strings and may be empty; a key left without a value is an error for `autonomy`, `split_threshold`, `self_contained_tickets`, and `ignore`.
- CONF-R08: (observed in code) `releases`, when present with a value, is a non-empty list of non-blank text slice names, kept in the given order, with no name listed twice; an absent key, or one left without a value, turns release slices off.
- CONF-R09: (observed in code) `host` is one of `github`, `gitlab`, `manual`; when the key is absent or left without a value, the host is detected from the `origin` remote URL, compared without case: a URL containing `github.com` means `github`, one containing `gitlab` means `gitlab`, anything else (including no `origin`) means `manual`; the loaded configuration records whether the host was detected.
- CONF-R10: (observed in code) The default branch is the branch `origin/HEAD` points to when it is set; otherwise `main` when it exists as a remote-tracking or local branch, otherwise `master` likewise, otherwise `main`.
- CONF-R11: (observed in code) Globs match whole repository-relative paths written with `/`: `**` matches any number of path segments including none (a trailing `/**` covers the folder's whole tree, `**/` at a segment start matches zero or more folders, and a `**` inside a segment matches across `/`), `*` matches any run of characters except `/`, `?` matches exactly one character except `/`, every other character is literal (no bracket classes, no brace alternatives), and a leading `./` on a pattern or a path is ignored.
- CONF-R12: (observed in code) A glob in `tests`, `code`, or `ignore` that contains a backslash is an error telling the person to use `/` between folders.
- CONF-R13: (observed in code) A file is a test file when it matches `tests` and is not excluded; it is a code file when it matches `code`, does not match `tests`, and is not excluded; a file matching both is a test file; an excluded file (matching `ignore`, or a framework file) is neither.
- CONF-R14: (observed in code) Every path listed under `files` in `kitchen.lock`, and the same path with the `.kitchen-new` suffix, is excluded like `ignore` even when the project's globs cover it; with no `kitchen.lock`, or a lock with no `files`, nothing is excluded this way; a lock that is not valid JSON, or whose `files` is not a table, is a configuration error that says to restore it from git history.
- CONF-R15: (observed in code) A test proves a criterion with the canonical tag, a bracketed upper-case story or task criterion reference (`[US-<CODE>-NN/ACn]` or `[TASK-<CODE>-NN/ACn]`) anywhere in the text; lower-case brackets and other ticket types are not tags.
- CONF-R16: (observed in code) The identifier tag form (`us_<code>_NN_acn` or `task_<code>_NN_acn`, any case) counts only when it ends at the end of the text or before a character that is not a letter or digit, and starts at the start of the text, after a character that is not a letter or digit, or after a lower-case letter or digit followed by an upper-case prefix (camel case); tags of both forms are reported in order of appearance with duplicates kept.
- CONF-R17: (observed in code) An epic code is an upper-case letter followed by one to nine upper-case letters or digits; epic IDs are `EP-<CODE>`; other ticket IDs are `US-`, `TASK-`, `DEC-`, or `SPK-` plus `<CODE>-` plus two or more digits; a ticket mentioned in free text counts only when not preceded by a word character or `-` and not followed by a word character (nor, for an epic, by `-`); criterion references are a story or task ID followed by `/AC` and a number; requirement IDs are `<CODE>-R` plus two or more digits, defined only by lines of the form `- <ID>: <text>`; ticket IDs sort by number, not as text.
- CONF-R18: (observed in code) A file carries the no-trace marker when its first ten lines contain `test-kitchen: no-trace`, in any comment syntax; the marker further down the file has no effect, and a marked file keeps its test or code classification.
- CONF-R19: (observed in code) Running `test_command` fills `{files}` with the selected test files, shell-quoted, root-relative, separated by spaces (empty for a full run); `{files:<dir>}` with the same files written relative to `<dir>` (slashes around `<dir>` ignored, files outside it reached with `../`, an empty `<dir>` behaving like `{files}`); `{report}` with the shell-quoted report path; every other brace text is left to the shell.
- CONF-R20: (observed in code) Git commands built through the shared library's git helper (the library's host detection, default-branch lookup, and file listing, and the git output the other scripts parse) run without a shell and with `core.quotePath=false`, color off, and signature lines off, so the person's git configuration cannot change what the scripts parse; a failing git command run through that helper reports the command and git's own message; the repository-root lookup runs a plain `git rev-parse --show-toplevel`.
- CONF-R21: (observed in code) The repository root is the git top level of the folder holding the scripts, whatever the current working directory; outside a git repository it is the parent of the scripts folder.
- CONF-R22: (observed in code) The project's file list holds `/`-separated repository-relative paths, sorted: without a revision, tracked files plus untracked files git does not ignore, skipping deleted ones; at a revision, the files of that commit; outside a git repository, every file under the root except inside hidden folders.
- CONF-R23: (observed in code) `python3 scripts/kitchen_lib.py --self-test` checks globs, tags, IDs, placeholders, and configuration validation without network and prints `PASS self-test` (exit 0) or one `FAIL` line per failure and a summary (exit 1); `--config` prints each loaded setting as `key: value` (exit 0) or each configuration problem as an `ERROR` line (exit 1); any other arguments print the usage text and exit 2.
- CONF-R24: (observed in code) PyYAML is needed only to read `kitchen.yml` and ticket frontmatter; without it, loading the configuration is an error that gives the install command, while the repository root, glob, and tag helpers still work.
- CONF-R25: (observed in code) Markdown is read the same with Windows line endings: ticket frontmatter is the `---` block at the start of a file, a delivery record's description follows a `<!-- change-request-description -->` or `<!-- pr-description -->` marker line, decision-log titles come from `### YYYY-MM-DD — <title>` headings (em dash), and a binary or unreadable file is skipped by the scans.
