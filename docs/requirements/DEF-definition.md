# DEF: Definition

The backlog and requirement conventions, `backlog_check.py` (validation, trace, coverage, and its modes), and the `/define` process (`playbooks/define.md`, the `define` skill). Written by `/define adopt` on 2026-11-25 from the code, the playbook, and the shipped skeletons; every line is unconfirmed until a person removes its marker.

## Requirements files

- DEF-R01: (observed in code) `backlog_check.py` reads every `.md` file under `docs/requirements/` except `README.md` files as a requirements file: the file must be named `<CODE>-<name>.md`, its requirements are the lines CONF-R17 defines (other text is free), and it reports an error for a misnamed file, a requirement whose code differs from the file's code, and an ID defined twice.
- DEF-R02: (observed in code) A requirement whose text starts `(superseded YYYY-MM-DD by <ID>)` no longer binds: it is left out of coverage and of the unconfirmed-requirement gaps, and naming a replacement that is not defined is an error.
- DEF-R03: (observed in code) A requirement whose text starts `(observed in code)` is recorded as unconfirmed, and `--gaps` lists each such requirement that is not superseded until the marker is removed.

## Tickets

- DEF-R04: (observed in code) Every `.md` file under `backlog/` is a ticket except `README.md` files and anything inside a folder named `delivery`; a ticket that is not UTF-8 text, has no `---` frontmatter block, has invalid YAML frontmatter, or whose frontmatter is not a mapping is an error.
- DEF-R05: (observed in code) Every ticket needs `id`, `type`, `title`, `owner`, `assignee_type`, and `status`, and every ticket but an epic also needs `epic`, `source_reqs`, and `blocked_by`; `type`, `status`, `assignee_type`, and `priority` must take one of their listed values, `refined` must be a `YYYY-MM-DD` date, `adopted` and `hotfix` must be true or false, `source_reqs`, `blocked_by`, `fixes`, and `code` must be lists, `code` is allowed on epics only, and decisions must have `assignee_type: human`; each violation is an error, and an unknown field is a warning.
- DEF-R06: (observed in code) A ticket's ID must match its type (`EP-<CODE>` for epics; `US-`, `TASK-`, `DEC-`, or `SPK-` plus `<CODE>-<nn>` with two or more digits for the rest) and be unique; an epic is a file named `epic.md` in its own folder `backlog/<CODE>-<slug>/` directly under `backlog/`; every other ticket is named `<ID>-<kebab-case-slug>.md`, names an existing epic, lives in that epic's folder, and carries that epic's code; each violation is an error.
- DEF-R07: (observed in code) Every `blocked_by` entry must name an existing ticket other than itself, every `source_reqs` entry a defined requirement, every `fixes` entry a live criterion in `<ticket>/AC<n>` form, and every `<ticket>/AC<n>` reference in a ticket body a live criterion; a `done` ticket with a blocker that is not `done` is an error while a `ready` one is allowed, and each `blocked_by` cycle is reported once.
- DEF-R08: (observed in code) Stories and tasks list their criteria under `## Acceptance criteria` as `- AC<n>: <text>` bullets whose numbers only grow; `(removed YYYY-MM-DD, <reason>)` keeps a number as a non-live placeholder; a story's live criterion must start with `Given `, a task's must not be empty, and each violation is an error.
- DEF-R09: (observed in code) A ticket other than an epic that is `ready`, `in-progress`, or `done` must have an owner that is not empty or `TBD`, a `release` when `kitchen.yml` lists releases (stories, tasks, and spikes), at least one live criterion (stories and tasks), and at least one `source_reqs` entry (stories); each violation is an error.
- DEF-R10: (observed in code) In a `ready`, `in-progress`, or `done` story or task, each `## Open questions` bullet must start with `None` or name a DEC or SPK ticket that exists, and when a named DEC or SPK is not `done` and not in `blocked_by`, the text after `Until decided:` must name one of the ticket's live criteria; each violation is an error, and `draft` tickets may hold unanswered questions.
- DEF-R11: (observed in code) When `kitchen.yml` lists `releases`, a ticket's `release` must be one of them, a deferred ticket's release must be the last slice, and no unfinished blocker may sit in a later slice than the ticket it blocks (errors); when no releases are listed, a `release` field is ignored with a warning.
- DEF-R12: (observed in code) When `kitchen.yml` sets `self_contained_tickets: true`, a ticket body that links to a repository file or names a repository path or document is an error per occurrence; links to `http(s)` addresses are allowed, and with the setting off neither is checked.

## Trace

- DEF-R13: (observed in code) In test files (the `tests` globs), a tag in either form (`[<ticket>/AC<n>]` or the lowercase identifier form) must name a live criterion of an `in-progress` or `done` ticket, otherwise it is an error; tags outside test files prove nothing.
- DEF-R14: (observed in code) A `done` story needs a tagged test for every live criterion (an error names the untagged ones), an `in-progress` story with untagged criteria gets a warning, and an `adopted: true` done story's untagged criteria are test debt instead of errors, listed by `--test-debt` as `DEBT` lines with exit 0.
- DEF-R15: (observed in code) In code and test files, every line holding one of the four to-do marker words named in `backlog/README.md` must name an existing ticket ID, and every decision ID mentioned must exist (errors, reported per line or per file); a mention of a decided DEC is a warning to revisit that seam.
- DEF-R16: (observed in code) `backlog_check.py` reads no file excluded from the scans (CONF-R13, CONF-R14), ticket and requirement files included, and does not scan a file carrying the no-trace marker (CONF-R18) for tags, to-do markers, or decision mentions, so its tags prove nothing.

## Command line and reports

- DEF-R17: (observed in code) A plain run prints one summary line with the count of each ticket type, errors, and warnings, then one line per finding as `<label> <file or ID>: <message>`, and exits 1 only when there are errors; a `kitchen.yml` configuration problem is printed as `ERROR` lines and exits 1.
- DEF-R18: (observed in code) A requirement that is not superseded, does not belong to an epic with `status: deferred`, and is cited by no story or task that is not deferred is reported as "not cited by any story or task": a warning normally, an error that makes the run exit 1 with `--strict`.
- DEF-R19: (observed in code) `--pr-body=FILE` (repeatable) also checks a change-request description, or the text after the marker line of a delivery record: `## Gaps found`, `## Decisions`, and `## Platform changes` must exist with at least one bullet or a single `None` bullet; every gap bullet names a ticket; every decision or platform-change bullet ends `Log: <title>` naming an existing decision-log heading (`### YYYY-MM-DD — <title>`) or names a done DEC; every ticket ID named must exist; HTML comments are ignored; an unreadable file is an error.
- DEF-R20: (observed in code) `--gaps` prints one `GAP` line for each open DEC or SPK (not `done` or `deferred`), each `draft` story or task, each unanswered open question of an unfinished story or task, each `ready` or `in-progress` story, task, or spike without `refined:`, each uncovered requirement, and each unconfirmed observed requirement; it exits 1 when it finds a gap or the backlog has validation errors (with a `WARN` line saying so), and prints nothing and exits 0 otherwise.
- DEF-R21: (observed in code) `--gaps` also reports a project with nothing defined: `docs/product.md` missing, unreadable, or holding only headings and comments; no requirement defined; and code files no epic claims, as one line with their count while no epic declares `code:` and one line per unclaimed code file once any epic does.
- DEF-R22: (observed in code) `--refine` prints `REFINE` lines for unfinished, non-deferred tickets: stories with more live criteria than `split_threshold`, tickets citing a superseded requirement (done ones told that a change becomes a new ticket), open questions naming a DEC or SPK that is done, tickets with no release while releases are on, done hotfixes without `refined:`, and `in-progress` tickets whose branch (the file name without `.md`, lowercased) is not on origin; it always exits 0, and when origin's branches cannot be listed it warns and skips that check.
- DEF-R23: (observed in code) `--self-test` validates a small fixture project in a temporary folder, breaks it three ways, prints `PASS self-test` or one `FAIL` line per failure, and exits 0 or 1, without a network; the modes `--gaps`, `--refine`, `--test-debt`, and `--self-test` cannot be combined with each other, with `--strict`, or with `--pr-body`, and such a combination or an unknown argument prints the usage and exits 2.

## Shipped skeletons and guides

- DEF-R24: (observed in code) An installed project starts with `docs/product.md` holding only the headings Vision, Users and roles, Capabilities, and Boundaries with comments (which `--gaps` reads as undefined), `docs/requirements/README.md` and `docs/architecture/README.md` holding only a heading and a comment describing their file formats (the ADR index section included), `docs/decision-log.md` holding the entry format in a comment, and `backlog/README.md` stating the ticket conventions the script enforces.
- DEF-R25: (observed in code) `guide/define.md` and `guide/concepts.md` describe the definition modes, the conventions, and what "fully defined" means for people who do not read the playbook.

## The define process

- DEF-R26: (observed in code) `/define [mode] [topic]` (or asking any agent to follow `playbooks/define.md` with a mode) runs one of nine modes: `new`, `change`, `sweep`, `refine`, `adopt`, `slice`, `bug`, `hotfix`, `ask`; without a mode it runs `new` when `docs/product.md` has no content, offers `adopt` when there is code but no ticket, and otherwise summarizes `--gaps` in one line and asks whether to run `change`, `refine`, or `sweep`.
- DEF-R27: (observed in code) In Claude Code, the `define` skill reads the playbook, `backlog/README.md`, and `AGENTS.md` first; asks each decision with AskUserQuestion, the recommendation first and marked "(recommended)"; runs the `ticket-reviewer` subagent in `ticket` mode for `refine`; gives each epic group to a subagent for `adopt` and large splits; and, when run headless, prints the decision briefs and writes nothing that needs a yes.
- DEF-R28: (observed in code) The agent never invents: it asks about three questions per round, each with a recommendation and why; what the person cannot answer becomes a DEC (a choice) or an SPK (something to verify); it asks whether each decision is needed now and proposes logged deferral when not; it presents only options recorded in `docs/` or the DEC, labeling its own as proposals; it records reported constraints verbatim with their certainty, verifies platform claims in official documentation, and never records secrets.
- DEF-R29: (observed in code) Every decision round uses the decision format: the next decision in plain words, "Your next action" in one line, "Already fixed" with IDs, lettered options each with its cost (the recommended one marked, a defer option with interim behavior), and "After you reply"; small sub-questions come as one table of at most five rows answered with "ok" or the rows to change.
- DEF-R30: (observed in code) At the end of each topic the agent shows each file, section, and text it will write and writes only after a yes that covers exactly that; requirements are written on the yes, stories and tasks only proposed and written on a yes, done tickets never rewritten (a change becomes a new ticket), the checkpoint that proposes `ready` asks for the owner, and `backlog_check.py` must exit 0 after writing.
- DEF-R31: (observed in code) After each decision the agent applies it in one pass, in order: the requirement or ADR, the affected criteria and tickets (removed criteria kept as dated placeholders), the epic's `## Open` line, the DEC's `## Outcome` and status, the open questions and `blocked_by` of the tickets it unblocks, a decision-log entry (`### YYYY-MM-DD — <title>`, newest first, with Decision, Why, Decided by, Recorded in; titles never renamed, a replaced entry gets `Superseded by:`), then `backlog_check.py`.
- DEF-R32: (observed in code) Definition goes through the layers in order (vision, users and roles, capabilities as epics, boundaries, requirements, architecture, stories and tasks), with epic codes chosen with the person, requirement IDs never renumbered or reused, a change of meaning superseding the old line; each requirement becomes a story, a task, or a constraint cited by a story, criteria come only from the requirement text, gaps become open questions naming a DEC or SPK, and a story over `split_threshold` gets a proposed split along a seam a user would notice.
- DEF-R33: (observed in code) `new` opens with one fixed question asking for a description of the product, drafts the vision in the person's words, works down the layers with a checkpoint per topic, writes stories as `draft` and refines them, offers the `AGENTS.md` project section and `slice`, and continues as `sweep`; `change` restates the change for confirmation, finds what it touches, asks about what is open, proposes requirement, ADR or DEC, and ticket changes at one checkpoint, applies, logs, checks, and refines the changed tickets.
- DEF-R34: (observed in code) `sweep` closes each `--gaps` line, the most blocking first, with the action the playbook's gap table names, until `--gaps` prints nothing or the person stops; `refine` handles each `--refine` finding with the person, reviews each ready or draft ticket in a fresh context in `ticket` mode, and sets `refined: <today>` when no CRITICAL is left and every WARNING is settled, reviewing again when criteria or open questions change later.
- DEF-R35: (observed in code) `adopt` builds a capability map with `code:` globs, then per epic proposes requirements marked `(observed in code)`, a DEC "Is this intended?" per suspected bug, `done` stories with `adopted: true` describing current behavior, and the epic's globs, writing them on a yes; it reports test debt as a separate list, walks the person through confirming each observed requirement, offers the `AGENTS.md` project section, and logs an "Adopt progress" entry at the end of each session.
- DEF-R36: (observed in code) `slice` asks its five questions in one message, proposes two to four slices in a table ordered so early slices wait on nothing slow, and on a yes writes `releases:` in `kitchen.yml`, a `release:` on every story, task, and spike (deferred ones in the last slice), and a decision-log entry.
- DEF-R37: (observed in code) `bug` records the report verbatim and triages it as a fix story with `fixes:` whose first test reproduces the bug, a missing requirement handled as `change`, or a DEC "Is this intended?"; `hotfix` proposes in one checkpoint a `ready` story with `hotfix: true` and an owner, a decision-log entry saying why the lane is used, and a draft follow-up task to refine it.
- DEF-R38: (observed in code) `ask` never writes: it answers from `docs/product.md`, requirements, ADRs, DECs, the decision log, and delivery records, citing each source and keeping its qualifiers, and when nothing covers the question it says "not defined in this repo" and offers to open a DEC or SPK.
- DEF-R39: (observed in code) The product counts as fully defined only when `--gaps` prints nothing, test debt never blocks it, and when delivery finds nothing ready, define takes the DECIDE list, then the REFINE list, then asks what to build next; define writes on a `docs/define-<topic>` branch and commits through a change request whose `## Ticket` starts `None. Defines`, with decisions citing their log entries, a delivery record, and the merge the autonomy level allows.
