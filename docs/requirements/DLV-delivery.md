# DLV: Delivery

How a ready ticket becomes merged, verified work: the deterministic steps and gates of `scripts/deliver.py`, the `/deliver` process in `playbooks/deliver.md`, the fresh-context reviewer in `playbooks/review.md`, `CONTRIBUTING.md`, and the Claude Code wrappers for delivery and review. Host adapters and CI templates belong to the host epic; the Claude Code guard belongs to the guard epic.

## `deliver.py next`

- DLV-R01: (observed in code) `deliver.py next` considers only stories, tasks, and spikes whose status is `ready` or `in-progress`; each one that is assigned to a person, has an unfinished blocker, has its branch taken (an open change request or a pushed branch), or is `in-progress` with no taken branch is printed as a `WAIT <ID>: <why>` line instead of being offered.
- DLV-R02: (observed in code) `deliver.py next` orders the offered tickets by release slice when releases are on (a ticket without a release last), then effective priority (a ticket inherits the highest priority of every unfinished ticket it blocks directly or transitively), then how many unfinished tickets it blocks directly (most first), then whether the person running it (`git config user.name`) owns it, then ID; it prints the first as `NEXT <ID> (<title>) branch `<branch>`` and each other one as a `READY` line, in that order.
- DLV-R03: (observed in code) When nothing is ready, `deliver.py next` prints a `NEXT none: …` line that says whether there is something to decide or refine, only work waiting, or nothing at all; it then prints a `DECIDE` line for each decision that is not done or deferred and blocks waiting work directly or through other unfinished tickets (most-blocking first, naming the tickets it blocks), followed by a `REFINE` line for each draft story, task, or spike in `next` order.
- DLV-R04: (observed in code) `deliver.py next` fails with exit 1 when the host cannot say which branches are taken.

## Ticket context and the change-request skeleton

- DLV-R05: (observed in code) `deliver.py context <ID>` prints the ticket's file, branch, type, status, owner, priority, release (when releases are on), hotfix and adopted markers, its epic with the epic's code globs, its live criteria (stories and tasks), the text of each cited requirement verbatim (or that it was not found), the accepted ADRs and those the ticket names with their status and path, the related tickets (named in the body, in `blocked_by`, or in `fixes`) with their status, and the ticket body.
- DLV-R06: (superseded 2026-11-25 by DLV-R50) (observed in code) `deliver.py pr-body <ID>` prints a change-request description skeleton with the sections Ticket, Plan, Gaps found, Decisions, Platform changes, Test changes, Review report, and Checks; for a story or task the Ticket line names the ticket, its requirements, and its status, and the Plan holds one row per live criterion followed by `Constrained by:`; for other ticket types the Ticket line starts `None. Delivers` and the Plan is `None.`; with autonomy `supervised` it adds empty plan and tests approval lines, and for a hotfix it adds a comment saying what the Decisions and Gaps found sections must hold.
- DLV-R50: `deliver.py pr-body <ID>` prints a change-request description skeleton with the sections Ticket, Plan, Gaps found, Decisions, Platform changes, Test changes, Review report, and Checks; for a story or task the Ticket line names the ticket, its requirements, and its status, and the Plan holds one row per live criterion followed by `Constrained by:`; for a spike the Ticket line starts `None. Spike <ID>: `, for a decision it starts `None. Decides <ID>`, and for both the Plan is `None.`; an epic is refused, since an epic is not delivered; with autonomy `supervised` it adds empty plan and tests approval lines, and for a hotfix it adds a comment saying what the Decisions and Gaps found sections must hold.

## `deliver.py gate red`

- DLV-R07: (observed in code) `deliver.py gate red <ID>` runs `test_command` on exactly the test files whose text tags the ticket (files matching the `tests` globs, never files listed in `kitchen.lock` or marked no-trace), with the JUnit report written to a temporary folder outside the repository, and prints the command it runs.
- DLV-R08: (observed in code) `deliver.py gate red` reads the JUnit report (a test case with a failure or error failed, one with a skip was skipped, any other passed), matches tags in the test name or class name, prints each tagged test's result, and passes only when every live criterion has at least one tagged test that ran and at least one that failed.
- DLV-R09: (observed in code) `deliver.py gate red` refuses tickets that are not stories or tasks, a story with no tagged test file, a ticket with no live criteria, a `test_command` without a `{report}` placeholder, a run that wrote no report (showing the end of the command's output), and a report that is not valid XML; a task with no tagged test passes, because the gate does not apply to it.

## Delivery records

- DLV-R10: (observed in code) `deliver.py record --body-file=F --branch=B [--cr=N] [--url=U]` writes the change-request description verbatim (line endings normalized) below a marker line, after a heading and lines naming the branch, the ticket, and the change request number and link when given; a ticket change request's record goes to the epic folder's `delivery/<ID>.md`, any other to `backlog/delivery/<branch with / as ->.md`; it prints the path.
- DLV-R11: (observed in code) `deliver.py record` replaces a record only when it belongs to the same change request (same branch and change-request lines); otherwise it writes `<name>-cr<N>.md` when `--cr` is given and fails asking for `--cr` when it is not; `--cr` must be a number.
- DLV-R12: (observed in code) A description is a ticket change request when its Ticket section starts with a story or task ID (markdown around the ID allowed); anything else, including a section starting `None.` that names a ticket later, is a non-ticket change request, for which `gate pr` refuses a ticket-named branch (`us-…`, `task-…`), checks the delivery record, and applies the review checks only when the branch's own commits change a code or test file.
- DLV-R13: (observed in code) `deliver.py gate pr` fails unless a delivery record for the change request (at its path, or a `-cr<n>` variant of it) is committed at the head and holds exactly the description, ignoring line-ending differences.

## `deliver.py gate pr`

- DLV-R14: For a ticket change request, `deliver.py gate pr` fails when the ticket does not exist, when the branch is not the ticket's file name lowercased, and when the Plan section has no row naming a live criterion exactly (a row for criterion 10 does not count for criterion 1).
- DLV-R15: (observed in code) `deliver.py gate pr` requires the Review report's last tally to show `CRITICAL: 0` and its last `Reviewed commit:` to be on the branch, with no code or test file changed by the branch's own commits after it; a merge commit counts as changing a file only when its combined diff shows a change of its own, so a clean merge of the default branch passes.
- DLV-R16: `deliver.py gate pr` fails when the ticket is not `done`, unless it is `in-progress` and the Ticket section says `in-progress` and names another ticket.
- DLV-R17: (observed in code) For a story, and for a task whose tests carry its tags, `deliver.py gate pr` requires exactly one commit named `test: <ID> failing tests` on the branch, and fails when any commit at or before it (merges included) changed a code file; a task with neither tagged tests nor that commit skips the test checks.
- DLV-R18: (observed in code) After the freeze commit, `deliver.py gate pr` fails when a live criterion had no tagged test at the freeze, when a criterion has fewer tagged tests now than at the freeze, and when a test file changed by the branch's own commits after the freeze is not named, by whole path or file name, under Test changes.
- DLV-R19: (observed in code) `deliver.py gate pr` fails when a branch commit after the freeze adds a line with a skip or focus marker (JavaScript and TypeScript runners, pytest, unittest, Go, JUnit 4 and 5, RSpec and minitest) to a test file; lines in product code and plain words are not flagged, and in a merge only lines new against every parent count.
- DLV-R20: For a `hotfix: true` ticket, `deliver.py gate pr` requires a Decisions bullet ending `Log: <entry title>` and a Gaps found section naming another ticket; with autonomy `supervised` it requires `Plan approved by:` and `Tests approved by:` lines in the Plan with a name that is not empty, `TBD`, `-`, or a `<…>` placeholder.
- DLV-R48: `deliver.py gate pr` reads the ticket files and `kitchen.yml` at the `--head` revision, as it reads the branch history, the tagged tests, and the delivery record there, so it judges exactly the revision it names.
- DLV-R51: When the ticket a change request delivers lists `replaces:`, the change request turns each replaced criterion into `- AC<n>: (removed YYYY-MM-DD, replaced by <ID>)` in its `done` ticket, the one edit a `done` ticket allows, and `playbooks/deliver.md` tells the agent to do so; `deliver.py gate pr` fails while any criterion the ticket replaces is still live at `--head`.
- DLV-R21: (observed in code) `deliver.py gate pr --from-record` reads the description from the one delivery record committed on the branch for that branch name, prints which record, and fails unless exactly one exists; without `--base` the gate measures from `origin/<default>`, else from the local default branch with a NOTE, else fails asking for `--base`, and every history check measures from the merge base of the base and the head.

## Merging

- DLV-R22: (observed in code) `deliver.py gate merge <N> --head=<sha>` fails on the manual host without calling a host CLI, and otherwise fails when the host cannot be read, when the pinned sha is not the change request's head, when the change request is not open, is a draft, does not target the default branch, or is not known to be mergeable, when no job named `check` passed on the head, and when any check is failing or pending.
- DLV-R23: (observed in code) `deliver.py gate merge` also fails when `origin/<default>` cannot be fetched, when the checkout is not a clean checkout of the change request's head, when the branch is behind `origin/<default>`, when the backlog has errors, when the live description breaks the description rules of `backlog_check.py --pr-body`, and when `gate pr` fails on the live description; it prints `PASS merge <N>` only when nothing failed.
- DLV-R24: (observed in code) `deliver.py merge-command <N> --head=<sha>` prints the one merge command the host adapter allows, pinned to the sha; it fails on the manual host and for a sha the host adapter refuses (HOST-R14), and with autonomy other than `merge` it still prints the command, with a NOTE on standard error that a person runs it.

## Checks, status, release notes, command line

- DLV-R25: (observed in code) `deliver.py check` runs `backlog_check.py`, then the self-tests of `kitchen_lib.py`, `hosts.py`, `backlog_check.py`, and `deliver.py`, then `check_command` when set or else `test_command` as a full run, stopping at the first failure with `FAIL <step>` and exit 1, and prints `PASS check` when all pass.
- DLV-R26: (observed in code) `deliver.py status` prints one screen: ticket counts per status (with a note when the backlog has errors), the ready tickets in `next` order without claimed ones (falling back to the branches seen at the last fetch, with a NOTE, when the host cannot be read), in-progress tickets with whether their branch is on origin, blocked tickets with their open blockers, open decisions and spikes, the gap count with the first five gaps, the test-debt count, and the five most recently committed delivery records with their dates.
- DLV-R27: (superseded 2026-11-25 by DLV-R49) (observed in code) `deliver.py release-notes [SLICE]` prints markdown for done stories and tasks: with a slice, those in that slice (refused when releases are off or the slice is not listed); without one, those whose delivery record was added since the last git tag, or all of them when there is no tag; stories appear as their "so that" outcome (or title) with the ID under their epic's title, tasks and hotfixes under "Other changes", and "No changes." when nothing is chosen.
- DLV-R49: `deliver.py release-notes [SLICE]` prints markdown for done stories and tasks, leaving out tickets marked `adopted: true` on every path: with a slice, those in that slice (refused when releases are off or the slice is not listed); without one, those whose delivery record was added since the last git tag, or all of them when there is no tag; stories appear as their "so that" outcome (or title) with the ID under their epic's title, tasks and hotfixes under "Other changes", and "No changes." when nothing is chosen.
- DLV-R28: (observed in code) `deliver.py` reports a usage error (unknown command, unknown or misspelled option, missing or malformed argument) on standard error with exit 2 before reading `kitchen.yml`, and reports configuration, git, host, file, and unknown-ticket errors as `FAIL` lines with exit 1.
- DLV-R29: (observed in code) `deliver.py --self-test` walks one story through `next`, `gate red`, `record`, and `gate pr` in a temporary git repository unaffected by the person's git configuration, checks that `gate pr` refuses a critical finding, and prints `PASS self-test` (exit 0) or each failure (exit 1).

## The `/deliver` process

- DLV-R30: (observed in code) `playbooks/deliver.md` defines `/deliver <ID>` (a story or task through 14 steps, a spike or decision through its variant, never an epic), `/deliver next` (the ticket `deliver.py next` names), and `/deliver all` (repeat until nothing is ready and the hand-off to define leaves nothing to do, or a question needs a person, ending with `deliver.py status`), with the same requests phrased for other agents.
- DLV-R31: (observed in code) The playbook takes the ticket `next` names and never reorders by judgment; on `NEXT none` it hands off to define (DEF-R39), one decision round at a time, resuming delivery under `/deliver all` once something is ready; a headless run never decides or marks a ticket ready, prints the decision briefs and the refine list, and stops.
- DLV-R52: Under `/deliver all`, each ticket is delivered in a fresh context where the agent can start one (a subagent or a new session), so one ticket's reading, diffs, and test output never carry into the next; the next ticket learns what earlier ones did from the repository only. An agent that cannot start a fresh context delivers the tickets one after another in the same session.
- DLV-R32: (observed in code) Steps 1 to 5 of the playbook: start on the ticket's branch from the up-to-date default branch and read `context`, the ADRs, the project rules, recent decisions, and the code; plan one row per live criterion from the `pr-body` skeleton kept outside the repository; ask the person's questions in one round and log the agent's own choices; run the plan review until no CRITICAL is left (and, when supervised, get the plan approved); claim by committing `in-progress`, pushing, and opening a draft change request.
- DLV-R33: (observed in code) Step 6 of the playbook: write tests tagged with their criteria, get `gate red` to pass with failures that are the missing behavior, run the tests review (and, when supervised, get the tests approved), then commit only test files as the single freeze commit `test: <ID> failing tests`, after which tests change only where they contradict the ticket or an ADR.
- DLV-R34: (observed in code) Steps 7 to 10 of the playbook: implement with comments tying decisions and open-DEC seams to their criteria; merge the default branch and pass `deliver.py check`; update documentation, commit code and tests, and run the diff review, handling each finding by severity; then file every gap, write the decision-log entries, set the ticket `done`, and pass `backlog_check.py`.
- DLV-R35: (observed in code) Step 11 of the playbook fills every description section, writes and commits the delivery record, runs `backlog_check.py --pr-body` and `gate pr`, pushes, then updates the description and marks the change request ready; an edited description needs the record rewritten, and messages that mention a merge or push are written to a file first.
- DLV-R36: (observed in code) Steps 12 to 14 of the playbook: with autonomy `merge` on GitHub or GitLab, wait for every check on the latest commit, read the head sha, and run exactly the command `merge-command` prints (running `gate merge` first where the guard does not); otherwise stop at "ready to merge" for a person who merges with a merge commit; after the merge watch the default branch's CI, do what `verify` says or report "not verified after deploy", return to the default branch, and report.
- DLV-R37: The playbook's variants: a testable task is delivered like a story, an untestable one skips step 6, and a partly testable one is a stop; a bug-fix story's first test reproduces the bug; a hotfix skips the questions and the plan review only; a spike and a decision are delivered on their own branches through non-ticket change requests; other changes use `fix/`, `chore/`, or `docs/` branches and still need a record and, when they touch code or tests, a final review.
- DLV-R38: (observed in code) Autonomy `merge` (default) lets the agent merge on green through the merge gate, `pr` stops at "ready to merge", and `supervised` also stops for a person to approve the plan and the tests; on the manual host pushed branches are claims, the agent runs the checks locally and pushes, and a person opens and merges the change request.
- DLV-R39: (observed in code) The playbook lists when the agent stops and asks (among them: unclean or unmerged work, a DEC option, an ambiguous criterion, unsettled user-visible behavior, any `docs/` or criteria change, a blocking gap, unprovable criteria, a weakened test, a failing check or gate it cannot fix, a failed CI run or deploy after the merge, platform or secret changes, credentials, supervised approvals, and boundary crossings), and says to ask everything in one round with a recommendation, to commit and push before waiting, and, headless, to print the questions and stop.
- DLV-R40: (observed in code) The playbook's ground rules: facts come from files and script output read in the session; criterion text is quoted when it matters; a gate's FAIL is final and is never worked around; agents never decide and code that meets an open DEC fails closed; nothing stays only in chat; work happens in this one checkout on the ticket's branch; credentials are never recorded.

## Fresh-context review

- DLV-R41: (observed in code) The playbook runs each review in a fresh context (the `ticket-reviewer` subagent in Claude Code, a new session elsewhere) given only the mode, the repository and ticket paths, the accepted ADR paths, each related DEC with its status, and the plan text, test file paths, or diff range, never the author's reasoning, and puts the report into the change request as it is.
- DLV-R42: (observed in code) `playbooks/review.md` makes the reviewer read-only (reading and running tests and the listed scripts only), takes the ticket's live criteria, cited requirements, and accepted ADRs as the only requirements, lists the inputs each of the four modes (`plan`, `tests`, `diff`, `ticket`) receives, and says to report only what was checked and what could not be.
- DLV-R43: (observed in code) `playbooks/review.md` defines what each mode checks: `plan` (cases per criterion, one row per criterion, scope, open choices, open DECs, constraints), `tests` (tags, failing for the right reason, intent, no skip or focus, running `gate red`), `diff` (completeness, correctness, coherence, capture, with an unfiled item CRITICAL), and `ticket` (ambiguity, testability, missing cases, scope creep, overlap, size, form).
- DLV-R44: (observed in code) `playbooks/review.md` defines the CRITICAL, WARNING, and SUGGESTION severities, orders findings most severe first with severity, location, what is wrong, and evidence, and ends every report with the tally line `CRITICAL: n, WARNING: n, SUGGESTION: n`, preceded in `diff` mode by `Reviewed commit: <full sha>`.

## Contributor guide and Claude Code wrappers

- DLV-R45: (observed in code) `CONTRIBUTING.md` points to the three playbooks and the rule files, states the principles of the process, lists each enforced rule with what enforces it, summarizes when an agent stops and asks, explains how to run the workflow in Claude Code, in other agents, and by hand, and lists the per-machine setup.
- DLV-R46: (observed in code) The `/deliver` skill accepts a ticket ID, `next` (or nothing), or `all`, follows `playbooks/deliver.md`, and adds only Claude Code mechanics: reviews through the `ticket-reviewer` subagent, questions through one AskUserQuestion round with the recommendation first, the hand-off through `/define`, the guard, no model of its own, and the headless behavior.
- DLV-R47: (observed in code) The `ticket-reviewer` agent has only the Read, Grep, Glob, and Bash tools, follows `playbooks/review.md` in the mode it is given, stays read-only, and ends its report with the closing lines the playbook gives for that mode.
- DLV-R53: Under `/deliver all`, the `/deliver` skill delivers each ticket in its own subagent, which follows `playbooks/deliver.md` for that ticket only and runs its reviews through the `ticket-reviewer` subagent. A question that needs the person is committed and pushed with the work, then returned to the main session instead of waited on; the main session asks it in one AskUserQuestion round and passes the answers back to that ticket's subagent, or, headless, prints it and stops. `/deliver <ID>` and `/deliver next` run in the current session as before.
- DLV-R54: The `/deliver` and `/define` skills tell the agent to read the playbooks and rule files with the file-read tool, one file per call, never combined with other commands in one shell call.
