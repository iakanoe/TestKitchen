# GRD: Merge guard

The Claude Code PreToolUse hook installed at `.claude/hooks/guard.py` (product source `template/claude/hooks/guard.py`, registered by `template/claude/settings.json`). The requirements marked `(observed in code)` were written by `/define adopt` from the code and its tests, describe what the guard does now, and are not confirmed by a person yet; a requirement without the marker was confirmed or decided by a person. "Ask" means the guard returns an ask decision (Claude Code prompts a person); "deny" means it refuses the call; "allow" means it prints nothing and the call goes through.

- GRD-R01: (observed in code) The hook is registered for PreToolUse with the matcher `Bash|Edit|Write|MultiEdit|NotebookEdit` and the command `python3 "$CLAUDE_PROJECT_DIR/.claude/hooks/guard.py" || exit 2`; a call of any other tool, or an empty shell command, is allowed without a decision.
- GRD-R02: (observed in code) The guard fails closed: hook input that is not a JSON object (or whose tool input is not an object) and any error raised inside the guard deny the call, and a guard that cannot start (a syntax error, a missing file) makes the registered command exit 2, which blocks the call.
- GRD-R03: (observed in code) The project root is `CLAUDE_PROJECT_DIR` (the top of its git checkout), else the git checkout that holds the guard file, never the command's working folder; when the project's scripts or `kitchen.yml` fail to load, every push and merge is denied with the load error, while other commands and edits outside protected paths go on.
- GRD-R04: (observed in code) A shell call that names a push or a merge (a git, gh, or glab command carrying the word, also spliced or quoted; an unquoted bare `push` or `merge` word anywhere; a program that pushes without the word, such as `git-push`, `send-pack`, `http-push`, or `subtree`; `glab mr accept`; or text run by a shell or interpreter that contains the word) must be plain shell, or it is denied: words of letters, digits, and `._/:=+,@-`, single quotes, double quotes without `$`, backticks, or backslashes, the separators `;`, `&&`, `||`, `|`, and newlines, and `#` comments of plain words; no control characters, background `&`, or `|&`. Path parts (`tests/push.test.ts`) and quoted words in ordinary programs do not name a push or a merge.
- GRD-R05: (observed in code) In a call that names a push or a merge, every program must be one the workflow uses, or the call is denied: `git` with one of the subcommands push, add, commit, status, log, diff, show, fetch, pull, merge, merge-base, rev-parse, branch, switch, checkout, stash and only the options the workflow uses (no git options before the subcommand); `git fetch` and `git pull` only from origin by branch name; the `gh pr`, `gh run`, `glab mr`, and `glab ci` workflow subcommands; `python3 scripts/deliver.py` and `python3 scripts/backlog_check.py`; `rg` without `--pre`; and `echo`, `cat`, `head`, `tail`, `wc`, `grep`, `ls`, `true`.
- GRD-R06: (observed in code) A push is allowed only as `git push [-u|--set-upstream] origin <branch>` (optionally with `-n`, `--dry-run`, `-q`, `-v`), naming one existing local branch that is not the default branch (compared without case); a bare push, another remote, several branches, a refspec, a wildcard, `HEAD`, a `refs/`-style prefix, a branch that does not exist locally, or any other option is denied.
- GRD-R07: (observed in code) A push is denied unless it runs from the project's own checkout (any subfolder of it), and every push is denied while `remote.origin.push` or `remote.origin.mirror` is set.
- GRD-R08: (observed in code) A push that is otherwise allowed but forced (`-f`, any `--force…` option, or a `+` before the branch) asks a person.
- GRD-R09: (observed in code) The only merge the guard allows is, alone in its call, word for word the command the configured host adapter's `merge_argv(<number>, <sha>)` returns (the command `deliver.py merge-command` prints): on GitHub `gh pr merge <number> --merge --match-head-commit <40-hex sha>`, on GitLab `glab mr merge <number> --sha <40-hex sha> --auto-merge=false --yes`; options that bypass, defer, squash, or rebase, extra, reordered, or `=` forms of options, a branch name, a URL, a short or uppercase sha, and the other host's merge command are denied, and the denial names the expected shape.
- GRD-R10: (observed in code) Before allowing a merge of the right shape, the guard requires the call to run from the project's checkout and runs `deliver.py gate merge <number> --head=<sha>` from the project root with its own interpreter; a failing gate, or one that does not finish within 300 seconds, denies the merge with the gate's output.
- GRD-R11: (observed in code) On the manual host, and when `kitchen.yml` sets `autonomy: pr` or `supervised`, every agent merge is denied with a message that a person merges the change request, without running the gate or calling the host.
- GRD-R12: (observed in code) A git, gh, or glab command whose program or subcommand is built at run time (`$'…'`, `$(…)`, backticks, `${…}`, a backslash) is denied; commands inside `$(…)`, backticks, `sh -c` and other shells' `-c`, `eval`, `xargs`, `find -exec`, text piped or fed to a shell, and interpreter one-liners are read and checked like top-level commands, while heredoc bodies read by `cat` are data.
- GRD-R13: (observed in code) `gh` and `glab` run without asking only for reads and the workflow's change-request steps, whichever host `kitchen.yml` names; any other built-in subcommand asks, and a top-level command that is not built in (an alias or extension) is denied.
- GRD-R14: A `gh api` or `glab api` call that may write (a method other than GET, fields or a form in any option form, input, or graphql) asks; one that also targets a merge or branch-moving endpoint or mutation (merge endpoints, auto-merge, rebase, git refs, contents, repository commits, files, or branches, the merge and ref mutations the guard lists) is denied; `gh repo sync` naming a repository or with `--force` is denied, and a bare `gh repo sync` asks.
- GRD-R28: A `gh api graphql` call with the `deleteRef` mutation is denied like REST calls that write git refs, sandbox mode included; `updatePullRequestBranch` is not denied and still asks as a host API call that may write.
- GRD-R31: (superseded 2026-11-26 by GRD-R35) A `gh api` or `glab api` call that writes branch protection is denied, sandbox mode included.
- GRD-R35: A host API call that may write (as GRD-R14 reads it) to branch protection is denied, sandbox mode included: on GitHub, `gh api` to `repos/{owner}/{repo}/branches/{branch}/protection` or a path under it, `gh api` to `repos/{owner}/{repo}/rulesets` or a path under it, and `gh api graphql` with the `createBranchProtectionRule`, `updateBranchProtectionRule`, `deleteBranchProtectionRule`, `createRepositoryRuleset`, `updateRepositoryRuleset`, or `deleteRepositoryRuleset` mutation; on GitLab, `glab api` to `projects/:id/protected_branches` or a path under it.
- GRD-R15: (observed in code) `glab mr create` (and `glab mr new`) with `--push`, with `--fill` or `-f` unless `--push=false` is given, or with `--auto-merge` is denied, with `--create-source-branch` asks, and `glab mr accept` is denied.
- GRD-R16: Every `git config` call that is not a read (`--get`, `--get-all`, `--get-regexp`, `--get-urlmatch`, `--list`, `-l`, `get`, `list`) asks, and so do `git -c`, `git --config-env`, and `GIT_*` variable assignments before git.
- GRD-R27: A git command asks as a git setting change only when git's subcommand, found after git's global options, is `config`; a `config` word elsewhere in the command (a file or folder name, as in `git add config`) does not make it ask.
- GRD-R17: (observed in code) A git subcommand that is not one of git's built-in commands spelled exactly and that matches a configured git alias in any case is denied when the alias pushes, merges, or runs a shell, and asks otherwise; any other word of a git command that matches an alias name asks.
- GRD-R18: (observed in code) A shell command that names a host token (the GitHub, GitLab, OAuth, and CI job token variable names, or a `PRIVATE-TOKEN` header) or names `.git`, `.gitconfig`, `.config/git`, `.config/gh`, or `.config/glab-cli` asks, reads included.
- GRD-R19: (observed in code) An Edit, Write, MultiEdit, or NotebookEdit call asks for a protected path: `docs/` (except the decision log), `.claude/` and `.git` at any depth, `.github/`, `.gitlab/`, `.gitlab-ci.yml`, `playbooks/`, `kitchen.yml`, `kitchen.lock`, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, the four framework scripts (`scripts/kitchen_lib.py`, `hosts.py`, `backlog_check.py`, `deliver.py`), every file `kitchen.lock` lists and its `.kitchen-new` copy, and the git, gh, and glab configuration files wherever they are; with no `kitchen.lock` only the fixed paths are protected, and with an unreadable one every file under `scripts/` is; other edits are allowed.
- GRD-R20: (superseded 2026-11-25 by GRD-R30) (observed in code) `docs/decision-log.md` is exempt from protection, for edits and shell writes alike, even though `kitchen.lock` lists it.
- GRD-R30: (superseded 2026-11-26 by GRD-R34) `docs/decision-log.md` is exempt from protection for edits and for shell writes that append to it, even though `kitchen.lock` lists it; a shell command that deletes or truncates it asks.
- GRD-R34: `docs/decision-log.md` is exempt from protection for appending, even though `kitchen.lock` lists it: a shell append (`>>`, `tee -a`) and an Edit or MultiEdit call go through; replacing or removing it asks: a `>` redirect to it, `cp` or `mv` onto it, `mv` or `rm` of it, `truncate`, in-place `sed -i` or `perl -i`, `git checkout` or `git restore` of it, and a Write call, which replaces the whole file.
- GRD-R21: (observed in code) Paths are compared after NFKC normalization and case folding, relative paths resolve against the call's working folder, and a path is checked both as written and with symbolic links resolved.
- GRD-R22: A shell command that may write a protected path asks: redirect targets (`>`, `>>`, `>|`, `&>`, a numbered descriptor, `>&` to a file, `<>`; not `>&N` or `/dev/null`), the files writing programs name (such as `tee`, `cp`, `mv`, `rm`, `touch`, `chmod`, `sed -i`, `perl -i`, `sort -o`, `uniq`, `dd of=`, `find -delete`, `curl -o`, `wget`, `tar -x -C`, `git checkout`/`restore`/`clean`, and `--output`-style options), and folders or globs that hold protected paths (`rm -rf docs`, `rm -rf *`, `git clean -fdx`); targets resolve against the call's folder and follow `cd`, and a write after a `cd` to a folder known only at run time asks; reading stays free.
- GRD-R26: (superseded 2026-11-26 by GRD-R32) After `cd -`, `popd`, or a `cd` inside a subshell `( … )` or a group `{ …; }`, the guard treats the folder as unknown, so every later write in the call asks, as after a `cd` to a folder known only at run time.
- GRD-R32: After `cd -`, `popd`, or a `cd` inside a subshell `( … )`, a group `{ …; }`, a script run by `sh -c`, `bash -c`, or another shell's `-c`, or a pipeline stage, the guard treats the folder as unknown, so every later write in the call asks, as after a `cd` to a folder known only at run time.
- GRD-R29: (superseded 2026-11-26 by GRD-R33) `git apply`, `patch`, and `git reset --hard` ask whenever the project has protected files, since they may change them through targets the guard does not read (a patch or the history).
- GRD-R33: `git apply`, `patch`, and `git reset --hard` ask in every project, since they may change protected files through targets the guard does not read (a patch or the history); the forms that do not write stay allowed: `git apply` with `--check`, `--stat`, or `--numstat` and without `--apply`, and `patch --dry-run`.
- GRD-R23: (observed in code) Code run by a shell or interpreter inline or on stdin asks when its text names a protected path or when it runs inside a protected folder.
- GRD-R24: (observed in code) Every check of a call runs before any ask is returned, so a denial anywhere in the call wins over an ask in another part of it.
- GRD-R25: (observed in code) With `KITCHEN_GUARD_SANDBOX` set to exactly `1`, asks let the call through without a prompt, except a force push, which still asks; denials and the merge gate are unchanged.
- GRD-R36: When the hook input carries a non-empty `agent_id` (a call made in a subagent), every ask the guard would give becomes a deny whose reason keeps the ask's reasons and tells the subagent to hand the step back to the main session, where the ask reaches the person. Sandbox mode (GRD-R25) applies first, so the asks it lets through still pass, and a force push, which asks even in sandbox mode, is denied in a subagent. Calls without an `agent_id` are unchanged.
