# HOST: Host adapters

- HOST-R01: (observed in code) `get_host` returns the adapter for the configured host: `github` (name "github", word "pull request", CLI `gh`), `gitlab` (name "gitlab", word "merge request", CLI `glab`), or `manual` (name "manual", word "change request", no CLI); any other host value gets the manual adapter.
- HOST-R02: (observed in code) The manual adapter never calls a host CLI: reading a change request raises NotSupported (a kind of HostError) saying a person checks and merges it, its merge command is None, and its open branches are only the branches pushed to origin.
- HOST-R03: (observed in code) Pushed branches are the branch names `git ls-remote --heads origin` lists; with no `origin` remote the set is empty, and when `origin` exists but cannot be listed a HostError is raised instead of a guess.
- HOST-R04: (observed in code) The GitHub adapter's open branches are the head branches of open pull requests from `gh pr list --state open --json headRefName --limit 1000`, plus the pushed branches.
- HOST-R05: (observed in code) The GitLab adapter's open branches are the source branches of open merge requests from `glab mr list --output json --per-page 100 --page <n>`, read page by page until a page holds fewer than 100 entries or 50 pages have been read, plus the pushed branches.
- HOST-R06: (observed in code) A host CLI that is not installed raises a HostError saying it is not installed or not on PATH; a host CLI that exits non-zero raises a HostError naming the command and carrying its stderr (or its stdout when stderr is empty).
- HOST-R07: (observed in code) The GitHub adapter reads a pull request with `gh pr view <n> --json number,state,isDraft,baseRefName,headRefName,headRefOid,mergeable,body,statusCheckRollup,url` and maps it to a change request: state OPEN, MERGED, CLOSED as open, merged, closed (other values lowercased), draft, base branch, head branch, head sha, body, url, and mergeable MERGEABLE as true, CONFLICTING as false, and anything else as unknown, keeping GitHub's own mergeable word for messages.
- HOST-R08: (observed in code) GitHub checks map as follows: a check run that is not COMPLETED is pending; a completed run with conclusion SUCCESS passes, SKIPPED or NEUTRAL is skipped, and any other conclusion fails; a commit status SUCCESS passes, PENDING or EXPECTED is pending, and any other state fails.
- HOST-R09: (observed in code) When a GitHub check ran several times on the pull request, only its latest run counts: runs are grouped by workflow name and check name, and the run with the latest start time wins.
- HOST-R10: (observed in code) The GitLab adapter reads a merge request with `glab mr view <n> --output json` and maps it to a change request: state opened, merged, closed as open, merged, closed (other values, such as locked, passed through), draft from `draft` or `work_in_progress`, target branch as base, source branch as head branch, `sha` (else `diff_refs.head_sha`) as head sha, description as body, `web_url` as url, and GitLab's own merge status word for messages.
- HOST-R11: (observed in code) GitLab mergeability is true only for detailed_merge_status `mergeable`, unknown while it is `checking`, `unchecked`, `preparing`, or `approvals_syncing`, and false for any other value; without detailed_merge_status, merge_status `can_be_merged` is true, `cannot_be_merged` is false, and anything else is unknown.
- HOST-R12: (observed in code) When the merge request's head pipeline has an id, the GitLab adapter reads its jobs with `glab api --paginate projects/:fullpath/pipelines/<id>/jobs`, keeps the job with the highest id for each job name, and maps job status: success passes; failed fails, or is skipped when the job may fail; canceled or canceling fails; skipped is skipped; manual is pending, or skipped when the job may fail; any other status is pending.
- HOST-R13: (observed in code) GitLab jobs count only when the head pipeline ran on the merge request's head commit; a head pipeline on another commit (a merged results pipeline included) yields one pending check naming the pipeline id and the first 8 characters of its commit, and no head pipeline yields no checks and no jobs call.
- HOST-R14: (observed in code) Reading a change request and building a merge command accept only a positive integer change-request number (surrounding spaces and leading zeros are dropped), and building a merge command only a full 40-character lowercase hexadecimal commit sha; anything else raises ValueError before any CLI runs.
- HOST-R15: (observed in code) The only GitHub merge command is `gh pr merge <n> --merge --match-head-commit <sha>`: a merge commit, pinned to the head commit, with neither auto-merge nor admin options.
- HOST-R16: (observed in code) The only GitLab merge command is `glab mr merge <n> --sha <sha> --auto-merge=false --yes`: pinned to the head commit, merged at once rather than queued, without a prompt, with the merge method left to the project's setting.
- HOST-R17: (observed in code) `python3 scripts/hosts.py --self-test` parses recorded gh and glab output without any CLI or network, prints a FAIL line per failure, and ends with `PASS self-test` (exit 0) or `FAIL self-test: <n> failure(s)` (exit 1); any other arguments print the usage text and exit 2.
- HOST-R18: (observed in code) The GitHub CI template (installed as `.github/workflows/check.yml`) runs a job named `check` on pull requests that are opened, synchronized, reopened, edited, or marked ready for review, and on pushes to `main` or `master`, with read-only repository contents and the full git history.
- HOST-R19: (observed in code) The CI templates of both hosts set up Python with PyYAML, carry the toolchain marker line `# TEST-KITCHEN: toolchain setup` directly above a placeholder that only prints a warning that the toolchain setup is not filled in, and then run `python3 scripts/deliver.py check`.
- HOST-R20: (observed in code) On pull requests, the GitHub CI job writes the live description (passed through an environment variable, never pasted into the script) to a file and runs `backlog_check.py --pr-body` on it; on pull requests that are not drafts it also runs `deliver.py gate pr` with that description, the head branch, the base sha, and the head sha.
- HOST-R21: (observed in code) The GitLab CI template (installed as `.gitlab-ci.yml`) runs merge request pipelines while a merge request is open and branch pipelines otherwise, never both for one push, with a job named `check` on the `python:3` image and a full clone (`GIT_DEPTH: "0"`).
- HOST-R22: (observed in code) In a GitLab merge request pipeline for a merge request that is not a draft (draft read from `CI_MERGE_REQUEST_DRAFT` or a title starting `Draft:`, `[Draft]`, or `(Draft)`), the `check` job runs `backlog_check.py --pr-body` on every delivery record the branch adds or changes and then `deliver.py gate pr --from-record` with the source branch, the diff base sha, and the head sha (the source branch sha when set, else the commit sha); for a draft it only prints that these checks run once the merge request is ready.
- HOST-R23: (observed in code) The pull request template and the merge request template give a description with the sections Ticket, Plan (a criterion-and-tests table and a "Constrained by:" line), Gaps found, Decisions, Platform changes, Test changes, Review report, and Checks, each with guidance and "None" defaults where a section may be empty; the merge request template also says GitLab CI reads the committed delivery record, so the record is rewritten, committed, and pushed after every edit of the description.
- HOST-R24: (observed in code) `guide/hosts.md` states the host settings the workflow needs: merge commits allowed (on GitLab, the merge method "Merge commit"), merged results pipelines off on GitLab, and a CI job named `check` that runs on every change request.
- HOST-R25: (observed in code) `guide/hosts.md` documents how the host is chosen, what each adapter runs, what the merge gate asks of every host, the adapter interface, and the steps to add a host.
