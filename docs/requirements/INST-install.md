## Running the installer

- INST-R01: (observed in code) `init.py` is one self-contained file that runs piped from the pinned URL (`curl -fsSL <raw init.py URL> | python3 - [mode] [options]`) or from a clone (`python3 <clone>/init.py [mode] [options]`), in one of three modes: `install` (the default), `update`, or `doctor`; `--target DIR` names the project's repository root (default: the current folder) and must be an existing folder, and `--help` lists every mode and flag.
- INST-R02: (observed in code) The release comes from `--source DIR` (a Test Kitchen checkout with a `template/` folder, whose version is its `init.py` `VERSION` or else its newest `## x.y.z` CHANGELOG heading), else from the checkout the running `init.py` sits in (only when it runs as a file and `--version` is not given), else from a shallow clone of the tag `v<version>` of the fixed repository URL (`--version vX.Y.Z`, default the running file's own version), which never waits for a password and is deleted after the run; a malformed `--version`, a `--source` without `template/`, or a `--source` whose version differs from `--version` stops with exit code 2, and a failed download stops with exit code 1 and suggests `--source`.
- INST-R03: Before installing, Python 3.7 or 3.8 stops with a sentence naming its version (exit 1; an older Python cannot parse the file), a missing `git` stops the run (exit 1), a missing PyYAML stops a real run with the command to install it but only warns on a dry run, and a missing `gh` or `glab` for the chosen host only warns.
- INST-R04: (observed in code) An install refuses a target inside a git repository that is not the repository root (exit 2, naming the root), plans `git init` for a folder that is not a git repository and runs it only after the plan is confirmed, warns about uncommitted changes and asks whether to continue (default no; a dry run only warns), and switches to `update` when the folder already has a `kitchen.lock`.
- INST-R05: (observed in code) The installer asks three questions, test-file globs, product-code globs, and the test command, unless `--tests` and `--code` (comma-separated, repeatable) and `--test-command` answer them; each question offers its guess from the folder as the default, and a test command without `{report}` is asked again on a terminal and otherwise stops the run with exit code 2 before anything is written.
- INST-R06: (observed in code) Guesses come from the project's files (git's tracked and untracked-but-not-ignored files, skipping dependency and build folders): the test command from `package.json` (vitest, then jest, then `node --test` in the test script), pytest configuration or mentions, or `go.mod`; test globs from top-level `tests/`, `test/`, `__tests__/`, `spec/` folders and test file names; code globs from `src/`, `lib/`, `app/`, `pkg/`, `cmd/`, `internal/`, Python package folders, or `**/*.go` for a Go module.
- INST-R07: Questions are read from the terminal, from `/dev/tty` when standard input is not one (a piped run); with `--yes` or without any terminal, each question takes its flag or its guess and a required answer with neither stops the run with exit code 2 naming the flag to pass, and without a terminal and without `--yes` any confirmation stops the run with exit code 2 before anything is written.
- INST-R08: (observed in code) The host is `--host github|gitlab|manual`, else detected from the `origin` remote (a URL containing `github.com` is github, one containing `gitlab` in any case is gitlab, anything else or no remote is manual); only the chosen host's CI and change-request template files are installed, manual installs none, and `kitchen.yml` gets `host: <host>` when `--host` was given or a commented `# host:` line with the detection reason otherwise.
- INST-R32: On Python 3.6 or older, `init.py` stops with a syntax error before its version check can run, and that is accepted; the code comment at the version check says that Python 3.7 and later get the sentence.

## What an install writes

- INST-R09: (observed in code) Template files are installed at mapped paths (`claude/` to `.claude/`, `github/` to `.github/`, `gitlab/gitlab-ci.yml` to `.gitlab-ci.yml`, other `gitlab/` files to `.gitlab/`, a trailing `.tmpl` dropped, everything else at the same relative path), without caches, editor files, or `.kitchen-new` copies, keeping executable bits, and with only the known `{{key}}` tokens replaced in `.tmpl` files.
- INST-R10: (observed in code) `--no-claude` installs neither `.claude/` nor `CLAUDE.md` and records the choice in `kitchen.lock`.
- INST-R11: (observed in code) Before writing, the installer shows a plan: the version and target, the source, the host and why, whether Claude Code files are installed, the three answers, one `create` or `exists` row per file (plus `git init` and `kitchen.lock` rows), and a note per CI file about its toolchain step; `--dry-run` stops after the plan and writes nothing, and otherwise the plan needs a yes (default yes; a no stops with exit code 1 and writes nothing).
- INST-R12: (observed in code) An install never overwrites an existing file, `kitchen.yml` included: the framework's version is written next to it as `<name>.kitchen-new`, and the install's next steps list every such copy to merge by hand and delete.
- INST-R13: (observed in code) The installed `kitchen.yml` holds the three answers as valid YAML (`tests`, `code`, `test_command`), the host line, and every optional key commented out with what it does, under a link to the configuration guide of the installed version.
- INST-R14: (observed in code) `kitchen.lock` is JSON holding `about`, `lock_format: 1`, the `version`, the `source` (`local checkout (commit <sha>)` or `<repository URL>@v<version>`, never a local path), `options` (`host`, `no_claude`, and the `toolchain` stacks filled), `files` (every framework path, `kitchen.yml` excepted, with the sha256 of the content installed or offered as `.kitchen-new`), and `side_by_side` (the files whose `.kitchen-new` copy is waiting when the lock is written).
- INST-R15: (observed in code) The CI file's step under `# TEST-KITCHEN: toolchain setup` is replaced for the stacks init recognizes, Node with npm (`package.json` and no yarn, pnpm, or bun lock file) and Python with pip (`requirements*.txt`, `pyproject.toml`, `setup.py`, or `setup.cfg`, and no Poetry, uv, or Pipenv file), both when both are present, and the marker then names the stacks; an unrecognized stack, a missing marker, or a marker with no step under it leaves the file as it is, with a note.
- INST-R16: (observed in code) After writing, the installer prints what to do next (merge side-by-side copies, fill the `## This project` section of `AGENTS.md`, review and commit, define the product), commits nothing, runs `doctor`, and exits 0 even when `doctor` reports a failure.

## Updating

- INST-R17: `update` needs a `kitchen.lock` (otherwise exit 2), never writes `kitchen.yml`, warns that `--tests`, `--code`, and `--test-command` only apply to install, and decides per framework file: unchanged locally and changed upstream is replaced, edited locally and unchanged upstream is kept, missing locally is restored, new upstream is added (or written as `.kitchen-new` when a file already sits there), and a file no longer shipped is listed but never deleted and leaves the lock.
- INST-R18: (observed in code) A framework file edited locally and changed upstream is a conflict: the person keeps theirs (the new version written as `<name>.kitchen-new`), takes the new version, or sees a unified diff and is asked again; `--yes` keeps theirs, and the summary lists the files kept.
- INST-R19: (observed in code) `update` shows its plan (the versions, source, host, Claude Code choice, one row per changed file, the count of unchanged files) and the CHANGELOG migration notes of every release after the installed version up to the new one, oldest first; it warns when the new version is older than the installed one, `--dry-run` writes nothing, a real run needs a yes, and afterwards it rewrites `kitchen.lock`, prints a summary, runs `doctor`, and exits 0.
- INST-R20: `update` installs for the host given with `--host`, else the host in `kitchen.lock`, else the detected one; switching hosts adds the new host's files and lists the old host's files as no longer shipped, and `--no-claude` can be turned on by an update (the Claude Code files are listed, not deleted) but never back off.
- INST-R30: An `update --host <host>` that changes the installed host leaves `kitchen.yml` untouched and prints that `host:` in `kitchen.yml` must be set to the new host.

## Doctor

- INST-R21: (observed in code) `doctor` is read-only (it writes no file, not even `__pycache__`), prints one `PASS`, `WARN`, `FAIL`, or `SKIP` line per check with what to do under each problem, ends with a summary line, and exits 1 when any check fails and 0 otherwise; the commands it suggests work from the project folder (the clone's absolute `init.py` path with `--target .`, or the pinned one-liner when piped).
- INST-R22: (observed in code) `doctor` checks Python, PyYAML, git, and the git repository; that `kitchen.lock` exists and is readable; that every framework file in it is present; and warns about every `.kitchen-new` copy still waiting, `kitchen.yml`'s included.
- INST-R23: (observed in code) `doctor` fails when `kitchen.yml` is missing, not valid YAML, has unknown keys, lacks non-empty `tests` and `code` glob lists or a non-empty `test_command`, has an invalid `host` or `autonomy`, or has a `test_command` without `{report}`, and warns about each `tests` or `code` glob that matches no file outside `ignore`.
- INST-R24: (observed in code) `doctor` fails unless `.claude/hooks/guard.py` exists, a `PreToolUse` hook in `.claude/settings.json` runs it, and neither `.claude/settings.json` nor `.claude/settings.local.json` sets `disableAllHooks`; it skips this check, with a reminder, for an install made with `--no-claude`.
- INST-R25: `doctor` warns when `kitchen.yml` or the `origin` remote names another host than the one the CI files were installed for, skips the CI check for the manual host, fails when a locked CI file is missing, warns while a CI file's toolchain step is still the placeholder (and passes one edited by hand), and warns when the host's CLI is missing or not signed in.
- INST-R26: (observed in code) `doctor` runs `scripts/backlog_check.py` and the `--self-test` of every locked `scripts/*.py` that offers one, failing with the end of their output when they fail.
- INST-R31: When `kitchen.yml` or the `origin` remote names another host than the one the CI files were installed for, `doctor`'s fix offers both directions: set `host:` in `kitchen.yml` to the installed host, or run `update --host <the other host>`.
